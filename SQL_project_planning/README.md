In this question, I encountered the Gaps and Islands problem in SQL (classic data analysis problem), in which islands are grouped by a continuous sequence of numbers, and there are gaps in the sequence when the numbers break away from their usual pattern. The first thing I do is I create an ordered_records Common Table Expression (CTE) which holds the temporary result set of the 'Projects' table attributes, ORDERED BY end_date in ASCENDING ORDER. Then, I calculate the date difference between the current end date and the end date of the record right before it. If this difference is 1, then it is a consecutive end date, but if not, then it is not consecutive and thus, the task is belonging to another project. I then create another CTE, called consec_check_row_num, which SELECTS task_id, start_date, end_date, and date_difference from the previous CTE, and also a column which will be used for the consecutive dates check that basically is populated with the difference in terms of dates, except this time, it is between the current record's end_date and the very first record's end_date. The first record's end date acts as a constant or reference point for which to reference the number of days that has passed between the first record's end date and the current record's end date. There is also one more column included which is the addition of row numbers sequentially for all records, ORDERED BY end_date. The next CTE is called group_key, this is kind of like when the common Project_ID is formed between tasks belonging to that specific project. All the attributes are carried forth from the previous CTE, but there is an addition of segmentation_key (which acts similarly to a Project_ID), whereby it is derived by getting the absolute difference between the generic row_num (which keeps increasing by 1 regardless), and the consecutive_check which increases by more than 1 if the tasks are belonging to different projects. In the project_segmentation CTE, I include a project_row_num column which PARTITIONS or groups BY segmentation_key, whereby if the absolute difference described earlier, fluctuates, as in the increment step is more than 1 for the consecutive_check column value, and this therefore causes the difference to not sync up because one column is incrementing differently, compared to the other generic row_num column which is standardized to an increment of 1, then we can conclude that the current record's end date is not consecutive to the end date of the record right before it, and therefore, the segmentation_key will change, bearing in mind, that all the records are sorted in ORDER of ASCENDING end dates. There is also a max_row_num column populated for each record, denoting the maximum number of records existing in that PARTITION, group, project or set of tasks. This number is derived by counting all the tasks with a similar segmentation_key (project_ID-like column). The following two CTEs, project_start_dates, and project_end_dates, extract the start dates and end dates respectively for each project. The start date of a project corresponds to the start date of the first task of that project (where project_row_num = 1), whereas the end date of that same project corresponds to the end date of the last task of that project (where project_row_num = max_row_num). The last CTE calculates the number of completion days which is the difference between the start date and end date of each project. This is required in the final SELECT statement where the start_date and end_date attributes are populated FROM the JOINED result of project_start_dates and project_end_dates CTEs ON segmentation_key (project_ID-like column) as the joining key to be matched, with all of the records ORDERED BY an INCREASING number of completion days, and if there is more than one project with the same number of completion days, this query is set to ORDER BY ASCENDING ORDER in terms of start date.
